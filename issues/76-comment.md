Notes from prototyping an optimization server on top of the Queue Server runner. These are cases the proposal should cover:

- **Items that fail before producing data.** A plan that is rejected at execution or raises before `open_run` produces no data, so a blocking evaluator waits forever unless it checks the queue item. Every evaluator would need that check. Consider a small helper on `QueueserverClient`, e.g. `item_result(item_uid)`, returning the exit status, message, and `run_uids` from `history_get()`, and refetching only when `status()["plan_history_uid"]` changes.
- **Rejected submissions.** `submit_plan` should return the item UID and raise when `item_add` reports `success: False`, which it returns instead of raising when `request_fail_exceptions=False`; today that case counts as submitted. When submission fails or the evaluator raises, register the suggestions with `TrialFaultAware` optimizers. Today a rejected first plan of `run()` / `submit_suggestions()` never registers its suggestions.
- **Run references.** The runner no longer sees run UIDs. If callers need them (history, links to data), read the item's `run_uids` from the queueserver history after evaluation.
- **`stop()` and queued items.** Removing a still-queued item on `stop()` would leave a blocking evaluator waiting forever, unless evaluators can observe the removal. The conservative contract in the proposal avoids this.
- **ZMQ helper (option 2).** It must ignore runs with other correlation UIDs and let several runners share one listener. Today both fail: a second `start_listener` on the same client is ignored, and another runner's run fails the active run, or makes an idle runner register failures for suggestions it already ingested.
